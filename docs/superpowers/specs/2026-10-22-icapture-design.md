# iCapture 설계 문서

- 작성일: 2026-10-22
- 상태: 승인됨 (2026-10-23)
- 프로젝트 폴더: `~/github/iCapture`

> 표기 규칙: **(결정)** 은 사용자가 직접 정한 것, **(설계자 판단)** 은 대화 중 Claude가 정하고 사용자에게 알린 것, **(빌더 재량)** 은 구현하는 사람이 정해도 되는 것이다.

## 1. 무엇을, 왜 만드나

화면에 보이지만 드래그로 복사할 수 없는 텍스트가 있다. 이미지로 된 문서, 원격 데스크톱, 영상 속 코드 같은 경우다. 지금은 캡처 앱과 일반 OCR(광학 문자 인식)로 해결하고 있는데, 오타가 너무 많다. 대표적인 예가 SQL의 `select`에서 소문자 `l`을 숫자 `1`로 읽는 경우다. 코드는 한 글자만 틀려도 실행이 안 되니, 결국 원본과 한 글자씩 대조하게 된다.

iCapture는 **단축키 한 번으로 영역을 캡처하고, AI 비전 모델이 문맥을 이해하며 텍스트를 읽어 주는 맥 메뉴 막대 앱**이다. 글자 모양만 보는 OCR과 달리, 모델은 "SQL에 `se1ect`라는 단어는 없다"는 걸 안다. 그래서 `l`/`1`, `O`/`0` 같은 혼동이 크게 준다.

기존 캡처 앱은 iCapture로 대체한다. 캡처부터 인식, 결과 표시, 이력 관리까지 iCapture가 혼자 처리한다. **(결정)**

### 성공의 모습

- 캡처해서 붙여 넣은 SQL을 손대지 않고 그대로 실행할 수 있다. 키워드, 식별자, 따옴표, 한글 주석과 문자열, 들여쓰기와 줄바꿈까지 원본과 같아야 한다.
- 혹시 틀릴 수 있는 글자는 화면에 표시돼서, 사용자가 그 부분만 확인하면 된다.
- 단축키를 누른 뒤 결과가 뜨기 시작하기까지 1~2초, 다 나오기까지 4~5초 정도를 목표로 한다. **(결정: 정확도가 높다면 4~5초까지는 기다릴 수 있음)**
- 속도와 정확도가 부딪히면 정확도가 먼저다. 5초를 넘겨도 괜찮다. 대신 사용자가 "지금 분석 중"이라는 걸 항상 알 수 있어야 한다. **(결정)** 표시 방법은 5.2절.

### 실패로 보는 경우 (anti-goals)

- 결과가 "대충 맞는" 수준이라 결국 원본과 대조해야 한다면 실패다.
- AI가 친절하게 원본을 고쳐 버리면 실패다. 문법을 바로잡거나, 오타를 수정하거나, 쿼리를 정리하는 식으로 말이다.
- 결과 앞뒤에 "다음은 추출한 텍스트입니다" 같은 설명이 붙거나, 코드 블록 기호(```)로 감싸져서 붙여 넣은 뒤 지워야 한다면 실패다.

## 2. 범위

### 하는 것 (goals)

1. 전역 단축키 `⌘⇧2`로 화면 영역을 선택해서 캡처한다. **(결정)**
2. 캡처 이미지를 AI 엔진에 보내 텍스트를 추출하고, 결과 창에 스트리밍으로 보여 준다.
3. 결과 텍스트를 편집할 수 있고, 전체를 복사할 수 있다.
4. 헷갈릴 수 있는 글자를 노란 밑줄로 표시한다.
5. 엔진을 Claude(클라우드)와 Nativ(로컬 LLM) 중에서 골라 쓸 수 있다.
6. 최근 캡처 10개를 이력으로 보관하고 다시 열 수 있다.

### 하지 않는 것 (non-goals) **(설계자 판단)**

- 동영상이나 화면 녹화
- 캡처 이미지 위에 그림을 그리거나 주석을 다는 기능
- 번역, 요약 같은 텍스트 가공
- App Store 배포, 샌드박스 대응, 다국어 UI. 개인이 직접 빌드해서 쓰는 앱이다.
- 전체 화면 캡처나 창 단위 캡처. 영역 선택만 지원한다.
- 이미지 자체를 내보내는 기능(이미지 클립보드 복사, 파일로 저장, 끌어다 놓기). 기존 캡처 앱도 텍스트 추출용으로 쓰던 앱이었으니, iCapture도 텍스트에만 집중한다. **(설계자 판단)**

## 3. 대상 텍스트와 출력 형식

캡처하게 될 텍스트는 네 종류다. **(결정)**

| 종류 | 특징 | 출력 형식 |
|---|---|---|
| SQL (한글 포함) | 주석, 별칭, 문자열 값에 한글이 섞인다. 키워드와 기호는 한 글자도 틀리면 안 된다. | 원문 텍스트 그대로. 들여쓰기와 줄바꿈을 보존한다. |
| 에러 로그 | 스택 트레이스, 타임스탬프, 경로, 숫자 코드가 많다. | 원문 텍스트 그대로. |
| 표 | 칸 구분이 핵심이다. | Markdown 표 |
| 엑셀 화면 | 표와 같지만 열 머리글(A, B, C…), 행 번호(1, 2, 3…), 격자선 같은 화면 장식이 함께 찍힌다. | Markdown 표. 열 머리글과 행 번호는 빼고 셀 데이터만 남긴다. |

- 결과는 주로 문서 편집기나 IDE(Zed, VS Code, IntelliJ)에 붙여 넣는다. **(결정)** 그래서 표는 Markdown 표로 내보낸다. **(설계자 판단)**
- SQL과 로그는 코드 블록 기호로 감싸지 않는다. **(설계자 판단)**
- 사용자가 종류를 고르지 않는다. 모델이 이미지를 보고 판단한다. **(설계자 판단)** 판별한 종류(SQL / 로그 / 표 / 기타)는 이력 목록에 배지로 표시하니, 앱이 이 값을 받을 수 있어야 한다. 받는 방식은 빌더 재량이다. 예를 들어 첫 줄에 태그를 붙이게 하고 앱이 떼어 내는 식이다.

### 모델에게 줄 지시문의 원칙 **(설계자 판단)**

- 보이는 그대로 옮긴다. 고치지도, 설명하지도 않는다.
- 원본에 오타가 있으면 오타도 그대로 둔다.
- 텍스트만 출력한다. 머리말, 맺음말, 코드 블록 기호는 붙이지 않는다.
- 공백과 들여쓰기, 줄바꿈을 보존한다.
- 표와 엑셀 화면은 Markdown 표로 출력한다. 엑셀은 행·열 머리글을 뺀다.
- `l`/`1`/`I`, `O`/`0`, `S`/`5` 같은 혼동은 주변 문맥(SQL 키워드, 식별자 규칙, 숫자 자리)으로 판단한다.

지시문의 실제 문구는 빌더 재량이다. 다만 아래 8장의 검증 세트로 정확도를 확인하면서 다듬어야 한다.

## 4. 사용 흐름 **(결정)**

1. 어떤 앱을 보고 있든 `⌘⇧2`를 누른다.
2. 화면이 살짝 어두워지고, 마우스로 드래그해서 영역을 고른다. `esc`를 누르면 취소된다.
3. 손을 떼면 결과 창이 뜬다. 왼쪽에 캡처 이미지, 오른쪽에 인식된 텍스트가 나온다. 텍스트는 글자가 나오는 대로 스트리밍으로 채워진다.
4. 헷갈린 글자에 노란 밑줄이 그어져 있다. 그 부분만 확인하고, 필요하면 직접 고친다.
5. "전체 복사"를 누르거나, 일부만 드래그한 뒤 `⌘C`로 복사해서 붙여 넣는다.
6. 결과가 이상하면 엔진을 바꾸고 "다시 인식"을 누른다.

- 모니터가 여러 대라면 마우스가 있는 화면에서 영역을 선택한다. **(설계자 판단)**
- 결과 창은 하나를 재사용한다. 새로 캡처하면 같은 창의 내용이 바뀐다. 앞의 결과는 이력에서 다시 열 수 있다. **(설계자 판단)**

## 5. 화면

### 5.1 메뉴 막대 아이콘 **(결정: Dock에 나타나지 않고 메뉴 막대에만 상주)**

아이콘을 누르면 이런 메뉴가 열린다. **(결정: 이력 화면 A안)**

```
영역 캡처                  ⌘⇧2
──────────────────────────────
최근 캡처
  SELECT u.id, u.name FROM…   3분 전
  java.lang.NullPointerExc…  12분 전
  | 컬럼명 | 타입 | 설명 |     1시간 전
  (최대 5개)
──────────────────────────────
모든 이력…                  ⌘Y
설정…                       ⌘,
종료                        ⌘Q
```

- 최근 캡처 항목을 고르면 결과 창이 그 이력으로 다시 열린다.
- 항목에는 텍스트 첫 줄 일부와 상대 시각을 보여 준다.
- 전역 단축키는 캡처 단축키 하나뿐이다. `⌘Y`, `⌘,`, `⌘Q`는 메뉴가 열려 있거나 iCapture 창이 앞에 있을 때만 동작한다. **(설계자 판단)**

### 5.2 결과 창 **(결정: 시안 C를 바탕으로, 선택 복사 버튼은 제거)**

```
┌──────────────────────┬──────────────────────────────────────────┐
│                      │ [엔진: Claude Sonnet ▾] [↻ 다시 인식]  [전체 복사] │
│   캡처 이미지          ├──────────────────────────────────────────┤
│                      │ SELECT u.id, u.name                       │
│                      │ FROM users u                              │
│                      │ WHERE u.level = 1̲                         │
│                      │   AND u.del_yn = 'N̲';                     │
│                      ├──────────────────────────────────────────┤
│                      │ 확인 필요 2곳 · Claude Sonnet · 1.8초         │
└──────────────────────┴──────────────────────────────────────────┘
```

- **왼쪽**: 캡처 이미지. 창 크기에 맞춰 비율을 유지한 채 보여 준다.
- **오른쪽 위 도구**: 엔진 선택, 다시 인식, 전체 복사.
  - "선택 복사" 버튼은 두지 않는다. 드래그한 뒤 `⌘C`로 복사한다. **(결정)**
- **오른쪽 텍스트**: 편집할 수 있는 고정폭 글꼴의 텍스트 영역.
  - 맥 기본 편집 단축키를 그대로 쓴다. `⌘Z` 되돌리기, `⌘⇧Z` 다시 실행, `⌘A`, `⌘C`, `⌘V`. **(결정)**
  - "다시 인식"으로 텍스트가 통째로 바뀐 뒤에도 `⌘Z`로 이전 결과로 돌아갈 수 있어야 한다. **(설계자 판단)**
  - 복사할 때는 서식 없는 일반 텍스트로만 클립보드에 넣는다. IDE에 붙여 넣었을 때 색이나 글꼴이 딸려 가면 안 된다. **(설계자 판단)**
- **노란 밑줄**: 헷갈릴 수 있는 글자에 표시한다(6.3절). 복사한 텍스트에는 영향을 주지 않는다.
- **상태 줄**: 확인이 필요한 곳의 개수, 사용한 엔진, 걸린 시간. 인식 중에는 진행 상태를 보여 준다. 오류가 나면 짧은 오류 메시지와 함께 "다시 인식"을 안내한다.
- SQL 키워드에 색을 입히는 구문 강조는 필수가 아니다. **(빌더 재량)**

#### 분석 중 표시 **(결정: 분석 중임을 알 수 있어야 함 / 방식은 설계자 판단, 시안 제시)**

정확도를 위해 5초를 넘길 수 있으니, 사용자가 "멈췄나?" 하고 의심하지 않게 단계마다 상태를 보여 준다.

| 단계 | 텍스트 영역 | 상태 줄 | 도구 |
|---|---|---|---|
| ① 이미지 읽는 중 (0초~) | 반짝이는 자리표시줄(skeleton) | `이미지 읽는 중… 0.4초` (시간이 계속 올라감) | 엔진·복사 비활성, "취소(esc)" |
| ② 텍스트 받는 중 | 스트리밍으로 줄이 채워지고 끝에 커서가 깜빡임 | `텍스트 받는 중… 3줄 · 2.1초` | 위와 같음 |
| ③ 정밀 검사 중 (필요할 때만) | 1차 결과를 흐리게 표시. 편집은 잠금, 복사는 가능 | `정밀 검사 중… 6.4초 · 편집은 검사 후` | "1차 결과 복사", "검사 건너뛰기" |
| ④ 완료 | 편집 가능. 검사로 바뀐 글자는 초록, 헷갈린 글자는 노랑 | `확인 필요 1곳 · 검사로 수정 1곳 · Sonnet · 7.2초` | 엔진, 다시 인식, 전체 복사 |

- 결과 창은 캡처 직후 바로 열고, 이미지는 즉시 보여 준다.
- ①~③ 동안 창 위쪽에 얇은 진행 막대가 흐른다. 상태 줄 오른쪽에는 몇 번째 단계인지 점(●○○)으로 표시한다.
- ③에서 편집을 잠그는 이유는 검사 결과로 텍스트가 바뀔 때 사용자가 고친 내용이 사라지지 않게 하기 위해서다. "검사 건너뛰기"를 누르면 1차 결과로 바로 ④가 된다.
- ①~③ 어디서든 `esc`나 취소 버튼으로 멈출 수 있다. 취소하면 그때까지 받은 텍스트는 남기고 편집 가능 상태로 둔다.
- 검사 단계가 없는 엔진·경우에는 ②에서 바로 ④로 넘어간다.
- 초록 표시(검사로 바뀐 글자)는 노랑과 마찬가지로 복사한 텍스트에 영향을 주지 않고, 사용자가 그 글자를 고치면 사라진다.
- 단계별 문구, 애니메이션, 색은 빌더 재량이다. 다만 "시간이 흐르고 있다"는 표시는 반드시 있어야 한다.

#### 메뉴 막대 아이콘 상태 **(설계자 판단)**

- 평소: 기본 아이콘
- 분석 중: 아이콘이 천천히 깜빡인다.
- 완료: 결과 창을 보고 있지 않았다면(다른 앱이 앞에 있음) 아이콘에 초록 점을 붙인다. 결과 창을 열면 사라진다.

### 5.3 이력 창 (`⌘Y`)

- 왼쪽에는 최근 10개 목록이 있다. 종류 배지, 첫 줄 일부, 시각을 보여 준다. 위쪽에는 텍스트 검색 칸이 있다.
- 오른쪽에는 결과 창과 같은 구성(이미지 + 텍스트)으로 선택한 이력을 보여 준다.
- "이력 비우기" 버튼을 둔다. **(설계자 판단)**
- 이력 창 안에서 텍스트를 고칠 수 있게 할지, 결과 창으로 열어서 고치게 할지는 빌더 재량이다.

### 5.4 설정 창 (`⌘,`) **(설계자 판단)**

- 기본 엔진: Claude Sonnet 5.5 / Claude Haiku 5.5 / Nativ(로컬)
- Claude API 키
- Nativ 서버 주소(기본 `http://127.0.0.1:8080`)와 선택 항목인 API 키
- 캡처 단축키. 기본은 `⌘⇧2`이고, 다른 앱과 겹칠 때를 대비해 바꿀 수 있다. `⌘⇧T`와 `⌘⇧S`는 IDE·편집기의 "닫은 탭 다시 열기", "다른 이름으로 저장"과 겹쳐서 기본값에서 뺐다. **(결정)**
- 로그인할 때 자동 실행 여부

## 6. 동작 방식

### 6.1 캡처

- 영역 선택 오버레이를 띄우고, 선택한 영역을 Retina 해상도 그대로 캡처한다. 작은 글씨일수록 해상도가 정확도를 좌우한다.
- 처음 캡처할 때 macOS "화면 기록" 권한이 필요하다. 권한이 없으면 시스템 설정의 해당 화면을 여는 안내를 띄운다.
- 캡처 API는 빌더 재량이다. 예를 들어 ScreenCaptureKit이 있다.

### 6.2 인식 엔진

엔진은 "이미지를 넣으면 텍스트가 스트리밍으로 나온다"는 같은 인터페이스 뒤에 숨긴다. 결과 창과 설정에서 엔진만 바꿔 끼우면 된다. **(설계자 판단)**

| 엔진 | 연결 방식 | 비고 |
|---|---|---|
| **Claude Sonnet 5.5** (기본) | Anthropic Messages API, 이미지는 base64 이미지 블록, 스트리밍(SSE) | 모델 ID `claude-sonnet-5-5`. 정확도 우선 **(설계자 판단)** |
| **Claude Haiku 5.5** | 위와 같음 | 모델 ID `claude-haiku-5-5`. 빠른 모드 |
| **Nativ (로컬)** | Nativ가 띄운 로컬 서버의 OpenAI 호환 `/v1/chat/completions`, `stream: true`. 이미지는 `image_url`에 `data:image/png;base64,…` 형태로 담는다 | **(결정: Nativ로 메모리에 올린 LLM에 연결)** |

Nativ 연결에 대해 확인한 사실은 다음과 같다(`~/github/nativ` 코드와 `Docs/features/developer.md` 기준).

- 서버 기본 주소는 `http://127.0.0.1:8080`이다. 호스트와 포트는 Nativ에서 바꿀 수 있다.
- OpenAI 호환 경로(`/v1/chat/completions`, `/v1/models`)와 Anthropic 호환 경로(`/v1/messages`)를 둘 다 제공한다.
- Nativ 자체 채팅 클라이언트(`Sources/NativServerKit/NativChatClient.swift`)도 이미지를 OpenAI 방식 `image_url`로 보낸다. 그래서 이 경로를 쓴다. Anthropic 호환 경로로 이미지를 보내는 건 확인하지 않았으니 쓰지 않는다.
- 서버 API 키를 설정해 두면 `Authorization: Bearer <키>`로 보내야 한다.
- 어떤 모델이 올라와 있는지는 `/v1/models`로 받아서 엔진 목록에 "Nativ: <모델명>"으로 보여 준다.
- Nativ 서버가 꺼져 있거나 이미지를 읽을 수 있는 모델이 없으면, 결과 창에 그 사실을 알리고 다른 엔진을 고르게 한다.

로컬 엔진의 속도는 맥 사양과 모델에 따라 크게 달라서, 4~5초 목표는 Claude 엔진에만 적용한다. **(설계자 판단)**

### 6.3 헷갈린 글자 표시 (노란 밑줄) **(결정: 시안 C 채택 / 방식은 설계자 판단)**

AI 모델은 글자마다 얼마나 확신하는지를 잘 알려주지 않는다. 그래서 다음 방식을 쓴다.

1. AI 엔진에 요청하는 동시에, 맥 내장 OCR(Apple Vision 프레임워크)로도 같은 이미지를 읽는다. 내장 OCR은 맥 안에서 빠르게 돌아간다.
2. AI 결과가 다 나오면 두 결과를 글자 단위로 비교한다.
3. 두 결과가 서로 다르게 읽은 글자 가운데, 혼동이 잦은 글자(`l`/`1`/`I`/`|`, `O`/`0`, `S`/`5`, `B`/`8`, `,`/`.`, `'`/`` ` `` 등)가 들어간 곳에 AI 결과 쪽에 밑줄을 긋는다.

- 표시할 기준은 "혼동 글자가 얽힌 불일치"다. 공백이나 줄바꿈 차이, Markdown 표 기호처럼 원래 형식이 달라서 생기는 차이는 표시하지 않는다.
- 비교 알고리즘과 정규화 방법은 빌더 재량이다.
- 밑줄은 사용자가 그 글자를 고치면 사라진다.
- Apple Vision이 한글이나 표를 잘 못 읽어서 불일치가 너무 많아지면, 밑줄이 의미를 잃는다. 이 경우 표시 기준을 조정하는 것도 빌더 재량이다. 목표는 "밑줄이 있는 곳만 보면 된다"는 신뢰를 주는 것이다.

### 6.4 이력 **(결정)**

- 최근 10개까지 보관한다.
- 11번째를 캡처하면 가장 오래된 것을 지우고 새 캡처를 넣는다. 먼저 들어온 것이 먼저 나가는 FIFO 방식이다.
  - 사용자는 이 동작을 "LIFO"라고 불렀다. 실제로 원하는 동작은 위 설명과 같다.
- 목록에는 최근 것이 맨 위에 보인다. **(설계자 판단)**
- 저장 위치는 프로젝트 폴더 안의 `~/github/iCapture/hist/`다. **(결정)** 캡처 이미지가 git에 올라가지 않도록 `hist/`는 `.gitignore`에 넣는다. **(설계자 판단)**
- 이력마다 다음을 저장한다. **(설계자 판단)**
  - 캡처 이미지(PNG)
  - 최종 텍스트. 사용자가 고쳤다면 고친 내용으로 저장한다.
  - 캡처 시각, 판별된 종류, 사용한 엔진
- 캡처 1회가 이력 1개다. "다시 인식"은 새 이력을 만들지 않고 현재 이력의 텍스트와 엔진 정보를 덮어쓴다. 사용자가 텍스트를 고치면 그 내용도 같은 이력에 저장한다(저장 시점은 빌더 재량). **(설계자 판단)**
- 저장 형식(폴더 구조, JSON 등)은 빌더 재량이다.
- 이력은 맥 밖으로 내보내지 않는다. 단, Claude 엔진을 쓰면 캡처 이미지가 Anthropic API로 전송된다. 사용자는 이 점을 알고 있고 괜찮다고 했다. 고객 데이터는 거의 없고, 대부분 개발 관련 텍스트다. **(결정)**

### 6.5 비밀 정보

- Claude API 키와 Nativ API 키는 macOS 키체인에 저장한다. 설정 파일이나 이력 폴더에는 쓰지 않는다. **(설계자 판단)**

## 7. 만드는 방법

### 결정된 것

- 맥 전용 네이티브 앱. Swift + SwiftUI. **(설계자 판단, 사용자 이의 없음)**
- `~/github/nativ` 프로젝트의 구조와 코드 스타일을 참고해서 맞춘다. **(결정)** Nativ는 사용자가 직접 만든 앱은 아니다. 참고할 점은 다음과 같다.
  - XcodeGen(`project.yml`)으로 Xcode 프로젝트를 생성하고, `Makefile`로 생성·빌드·서명·실행을 처리한다.
  - Swift 6.3, macOS 26 이상, Apple Silicon(arm64) 전용, Hardened Runtime
  - AppKit `AppDelegate` 위에 SwiftUI 화면을 얹는다. 메뉴 막대 아이콘은 `NSStatusItem`으로 만든다(`Sources/Nativ/AppDelegate.swift`).
  - 전역 단축키는 Carbon `RegisterEventHotKey`로 등록한다(`Sources/Nativ/Features/VoiceCapture/FnControlShortcutMonitor.swift`).
- Dock 아이콘 없이 메뉴 막대에만 상주한다(`LSUIElement`).
- 프로젝트 폴더: `~/github/iCapture`. 앱 이름: `iCapture`. **(결정)**

### 빌더 재량

- 모듈과 파일 구성, 외부 패키지 사용 여부(예: Anthropic API를 직접 HTTP로 호출할지)
- 영역 선택 오버레이의 세부 모양
- 이력 저장 형식
- 글자 비교 알고리즘
- 지시문 문구
- 오류 메시지 문구

## 8. 검증

정확도가 이 앱의 존재 이유다. 그래서 감으로 판단하지 않고, 정답이 있는 검증 세트로 확인한다.

- 검증 세트는 빌더가 만든다. 아래 종류별로 몇 장씩 캡처 이미지와 정답 텍스트를 짝지어 둔다.
  - 한글 주석과 문자열이 섞인 SQL. `select`, `level`, `del_yn`, `1`, `l`처럼 헷갈리는 글자가 많이 들어간 것으로 고른다.
  - Java/Python 스택 트레이스 같은 에러 로그
  - 표(웹 페이지, 문서)
  - 엑셀 화면(행·열 머리글 포함)
  - 작은 글씨, 어두운 테마 에디터 화면
- 엔진별로 정답과 결과가 글자 단위로 얼마나 일치하는지 보고, 걸린 시간을 기록한다.
- 기준은 이렇다. SQL과 로그는 Claude Sonnet 5.5에서 정답과 완전히 일치하는 것이 목표다. 혼동 글자가 틀렸더라도 그 자리에 노란 밑줄이 있으면 통과로 본다. 밑줄 없이 틀린 글자가 실패다. **(설계자 판단)**
- 첫 버전은 캡처 1회당 모델 호출 1회(스트리밍) + Apple Vision 비교로 만든다. 측정 결과가 기준에 못 미치면, 시간이 더 걸리더라도 정확도를 올리는 방식을 추가한다. 예를 들면 이미지 확대 같은 전처리나, 두 번째 검증 호출이 있다. 5초를 넘겨도 된다는 건 사용자가 직접 정했다. 그러니 엔진 인터페이스는 처음부터 "1차 결과 → 검증 → 최종 결과"처럼 단계가 여러 개인 경우도 담을 수 있게 설계한다. **(설계자 판단)**
- 숫자 목표(예: 일치율 몇 %)는 첫 측정 결과를 보고 사용자와 함께 정한다.
